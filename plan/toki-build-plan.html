01 · Reading

What the prototype is

Toki is a workspace messenger for a single company (“Acme”) that merges three products: Slack-style channels and DMs, a Huddle-style live room attached to every conversation, and a Google Meet-style call screen with captions, hand raising and screen sharing. Calls are not a separate app. The Meet button sits in every channel and DM header, the in-call chat is the conversation itself, and a sidebar shortcut lists the Meets running now.

The prototype is static design (no backend), written as interactive boards on one canvas. Content is Vietnamese while the UI is English with a language picker, so diacritic-aware search and full localisation are core requirements, not polish. The colour tokens reference apps/web/style.css, which suggests a web-first monorepo. It also includes enterprise controls you rarely see in a prototype: a tamper-evident audit log, retention, legal holds and JSONL exports.

03 · Architecture

Architecture

One TypeScript monorepo. A stateless API serves REST for reads and writes; a WebSocket gateway fans out realtime events; a self-hostable SFU carries audio, video and screen share. Postgres is the source of truth, Redis carries presence, typing and pub/sub, and object storage holds files. Background workers own anything scheduled: reminders, scheduled sends, retention, exports, link unfurls and captions.

Recommended stack
  • Web: React 18, Vite, TanStack Query, a virtualised message list, Tiptap/ProseMirror for the composer.
  • API: Node 22, Fastify, Zod contracts shared with the client, Drizzle or Prisma.
  • Realtime: plain WebSocket gateway, Redis pub/sub, per-conversation sequence numbers for gap-free resync.
  • Meet: LiveKit (open source SFU, simulcast, screen share, data channels for reactions and hand raise).
  • Search: Postgres FTS with unaccent for P1, a dedicated index in P3.
  • Desktop: Tauri shell around the web app in P5.
  • Mobile: React Native (Expo) with the LiveKit mobile SDK, sharing contracts with web.
  • Hosting: managed cloud, Singapore region. Kubernetes for API, gateway and workers; managed Postgres, Redis and S3; LiveKit on dedicated media nodes with TURN.
Why these choices
  • We run it as a managed service. Singapore keeps latency to Vietnam low (about 30–40 ms), and every component is open source, so moving region or self-hosting later stays possible.
  • LiveKit avoids writing an SFU and handles 5-to-50-person rooms; the prototype’s largest call shows 5.
  • Sequence-numbered events keep the “New messages” divider, unread badges and the Connected indicator honest after reconnects.
  • Shared Zod schemas keep the 12 Preferences tabs and the admin settings typed on both sides.
04 · Data model

Data model

Entities implied by the boards, grouped by the phase that first needs them. Every table carries workspace_id; tenant isolation is enforced in the API layer and with Postgres row-level security.

Identity · P0
  • Workspace: name, icon, settings JSON (link previews, blocked domains, permissions, edit window)
  • User: email, display name, full name, title, pronouns, phone, time zone, photo
  • Membership: role (owner / admin / member / guest), active flag
  • Session: device, last seen; supports “Sign out everywhere”
Conversations · P1
  • Conversation: kind (public, private, dm, group_dm), name, topic, description, archived_at, managers_only_post
  • ConversationMember: is_manager, notify_level, muted, starred, last_read_seq, follow
  • Message: seq, author, rich-text doc (JSON AST), thread_root_id, also_in_channel, edited_at, deleted_at, pinned_at
  • Reaction, Attachment (size, mime, storage key, expired_at), LinkPreview
  • ThreadFollow, Draft, ConversationTab
Meet · P2
  • MeetSession: conversation_id, sfu_room, started_by, started_at, ended_at, scheduled_for, calendar_event_id
  • Recording: meet_id, started_by, storage key, duration, attachment_id (P4)
  • GuestLink: meet_id, token hash, expires_at, revoked_at; GuestParticipant: name, admitted_by (P4)
  • MeetNotes: meet_id, summary, decisions, action items, model, posted_message_id (P4)
  • CalendarConnection: user, provider (Google, Microsoft), encrypted OAuth tokens (P4)
  • MeetParticipant: joined_at, left_at, device info
  • CaptionSegment (optional storage, off by default): speaker, text, t_start, t_end, language
  • Ephemeral, in Redis / data channel: speaking, muted, hand raised, reactions
Attention · P3
  • ActivityItem: kind (mention, reply, reaction, dm, reminder), target, read_at
  • LaterItem: message_id or free text, status (in_progress, done), remind_at, recurrence (RRULE)
  • ScheduledMessage: conversation, body, send_at
  • FileStar: user, attachment (synced across devices)
  • UserPreference (typed JSON, one row per user), VIP, HiddenPerson, Keyword, Status (text, emoji, clear_at)
Governance · P5 essentials, rest deferred
  • AuditEvent: at, actor, action (role.change, channel.create, …), detail, prev_hash, hash
  • RetentionPolicy: org-wide days or keep forever
  • LegalHold: conversation, note, created_by, released_at
  • ExportJob: scope (public / everything), status, file manifest, download URL
  • Invitation: email, role, channels, expires_at; ExternalConnection
Mobile & integrations · P6
  • Device: platform, push token, app version, last active (for the phone delay rule)
  • App: name, owner, scopes, redirect URLs, signing secret
  • AppInstall: workspace, approved_by, scopes granted, bot user id
  • ApiToken: install or bot, scopes, hash, last used
  • IncomingWebhook, SlashCommand, EventSubscription (topic, URL, delivery log)
Realtime events
  • message.created / updated / deleted
  • reaction.added / removed
  • thread.replied · read.updated
  • typing.started · presence.changed
  • conversation.updated · member.changed
  • meet.started / ended · meet.roster
  • activity.created · later.due
05 · Timeline

Timeline

Assumes 3 full-stack engineers, 1 realtime/media engineer, 1 mobile engineer from week 9, 1 designer shared with QA, and a part-time DevOps owner. Phases overlap where the work is independent: the media engineer starts Meet spikes during P1.

Mobile engineer hire

Role
  • Senior mobile engineer, React Native, 4+ years, with at least one app shipped to both stores.
  • Must have: Expo or bare React Native, push (APNs and FCM), offline sync, release pipelines (Fastlane or EAS).
  • Strong plus: WebRTC or LiveKit on mobile, CallKit and ConnectionService, Vietnamese and English.
  • Owns: P6a native apps end to end, store listings and review, and mobile on-call after launch.
Hiring timeline
  • Wk 0–1: job description signed off, posted, recruiter or agency briefed.
  • Wk 2–5: screening and a take-home task (build a chat screen against a mock API).
  • Wk 5–6: final round with the tech lead and media engineer; offer out.
  • Wk 9: start date (allows up to 3 weeks notice).
  • Wk 9–11: onboarding: repo, packages/contracts, design tokens, an Expo shell with sign-in.
Until they join
  • A full-stack engineer sets up the Expo project, the shared API client and CI build lanes in P0–P1 (about 3 days).
  • Apple Developer and Google Play accounts, bundle IDs and push certificates are requested in week 1, because approval can take two weeks.
  • The designer adapts the two phone boards into native navigation (tab bar, stack) by week 9.
Fallback triggers
  • No offer accepted by wk 8: bring in a contract mobile engineer or agency for P6a while hiring continues.
  • No one started by wk 12: web and desktop beta stays at wk 24; store launch moves to wk 32. Integrations stay on their dates.
06 · Phases

Phases

P0 · Weeks 1–2 · Foundations

Repo, identity, design system, realtime skeleton

  • Monorepo (apps/web, apps/api, apps/gateway, packages/contracts, packages/ui), CI, preview deploys, seed data matching the prototype’s Acme cast.
  • Port the prototype’s colour tokens (dark and light), type stack (Inter, JetBrains Mono) and density into packages/ui; build Button, Avatar with presence dot, Badge, Tabs, Menu, Dialog, Toggle, Select.
  • Sign-in: company OIDC/SAML, email sign-in with display name, and “Sign in as a test person” behind a dev-only flag.
  • i18n framework with English strings extracted from the boards; language picker on sign-in.
  • WebSocket gateway with auth, heartbeat and the Connected indicator.

Exit: a signed-in user sees the empty shell (rail + side panel) in both themes.

P1 · Weeks 3–8 · Messaging core

Channels, DMs, threads and the composer

  • Conversations: public and private channels, 1:1 and group DMs, browse, join, leave, create, archive.
  • Message list: day dividers, New messages marker, edit and delete, reactions, pins, typing indicator, inline code and code blocks, link unfurls with a fetch worker.
  • Composer with rich formatting toolbar, Aa toggle, mentions, emoji picker, file upload with progress, drafts, Enter vs Ctrl+Enter.
  • Thread pane: replies, follow/unfollow, “Also send to channel”, thread summary row in channel.
  • Read state and badges per conversation; side panel sections, Starred, unread bolding; Jump to (Ctrl K).
  • Channel header tabs (Messages, Files & links, Pins) and Channel details (topic, description, managers, members, managers-only posting).
  • Profile card and avatar menu; People and Channels directories with basic search.

Exit: the team can stop using its current chat tool for one project channel.

P2 · Weeks 7–13 · Meet

Live rooms in every conversation

  • Weeks 7–8 spike (overlaps P1): LiveKit deployment, TURN, token minting, room-per-conversation model.
  • Start or join a Meet from any channel or DM header; “More ways to join” (audio only, copy link); sidebar Meet list of rooms running now; system message in the conversation when a Meet starts and ends.
  • Call screen: tile grid with active-speaker ring, muted icon, raised-hand ring, call timer, participant count, channel context.
  • Controls: mute, camera, screen share, raise hand, emoji reactions, audio and video device settings, People panel, details, leave.
  • Meet chat panel that reads and writes the conversation itself, so the call’s discussion stays in history.
  • Pre-join device check, join muted, leave on screen lock (from Audio & video preferences).
  • Week 13: live captions in Vietnamese and English from a streaming ASR worker that detects language per speaker, so mixed-language calls caption correctly; toggle per participant.

Exit (internal dogfood): daily stand-up runs in Toki for two weeks with no fallback to another call tool.

P3 · Weeks 14–17 · Attention and retrieval

Activity, notifications, Later, Search, Files

  • Activity feed with filters (All, DMs, Mentions, Threads, Reactions), Unread only, Mark all as read.
  • Notification engine: per-channel level, keywords, DND with durations, working hours by time zone, VIP pass-through, hidden people, phone delay after desktop activity, email digest of missed mentions, hide message text.
  • Later: save messages, reminders (in 1 hour, tomorrow at the user’s configured time), recurring reminders, scheduled messages; tabs In progress, Completed, Scheduled, Reminders.
  • Search: Messages, People, Channels, Files tabs; diacritic-insensitive matching (“phat hanh” finds “phát hành”); highlighted hits; newest or best match; excluded channels; in-channel search.
  • Files view: All, My files, Starred (synced to the account), search by name, unavailable state for expired files.
  • Preferences: all 12 tabs wired to the typed preference store.

Exit: nobody on the dogfood team misses a mention for a week (measured from Activity read receipts).

P4 · Weeks 14–20 · Meet+ (runs alongside P3, led by the media engineer)

Recording, guest links, calendar, AI notes

  • Recording (wk 14–15): LiveKit Egress, composite layout to MP4 in object storage. Everyone sees a recording indicator and a consent notice on join. When the call ends, the file is posted into the conversation and appears under Files. Only the host or a channel manager can start or stop it.
  • Guest join link (wk 15–17): a signed link per Meet that expires. Guests type a name, see a pre-join device check and wait in a lobby until a member admits them. They get call chat only, with no workspace access. A link can be revoked from Meet details.
  • Calendar scheduling (wk 17–18): choose “Schedule a Meet” from the Meet menu or the /meet command. Connect Google Calendar and Microsoft 365 with OAuth to create the event with the join link and a guest link. The conversation gets a pinned upcoming-Meet card, and a reminder goes out 5 minutes before.
  • AI notes (wk 18–20): after the call, the caption transcript goes to Claude, which drafts a summary, decisions and action items in Vietnamese, English, or both side by side. By default the notes use the conversation’s usual language, and each Meet can override it. The result is posted as a thread reply on the Meet’s start message. Action items can be sent to Later with one click. Notes can be turned on or off for each Meet, and the room shows when notes are being taken.
  • New preferences: record by default (off), allow guests in my Meets, connected calendars, AI notes default.

Exit: a weekly all-hands with two outside guests is scheduled from the calendar, recorded, and its AI notes are posted without manual steps.

P5 · Weeks 19–24 · Beta, essential admin, mobile

What an internal rollout needs, then hardening

  • Essential admin: Workspace, People and Audit log tabs; roles, deactivate and reactivate, sign out everywhere; channel and @channel permissions; edit window; link previews and blocked domains; invitations by email. SSO accounts are provisioned automatically for company domains.
  • Audit events are written as a SHA-256 hash chain from P0, so the integrity verifier can ship later without a migration.
  • Responsive phone layout in the web app as a fallback; native apps are P6.
  • Classic navigation layout (workspace column, create a workspace), text size, compact list, Match my system theme.
  • Accessibility pass: screen-reader live region for new messages, underline links, reduced motion, image description reminder, keyboard map.
  • Desktop shell (Tauri) with native notifications and screen-lock detection.
  • Load test (1,000 concurrent users, 50-person Meet), security review, backup and restore drill, company beta.

Exit: company-wide rollout (beta) with an on-call rotation and published SLOs.

P6 · Weeks 12–28 · Native apps and integrations

App Store, Play and a public apps platform

  • Native apps (mobile engineer, wk 12–28): React Native with Expo, sharing packages/contracts and the API client with the web app. Includes the conversation list, channel, thread, DMs, Activity, Later and search screens, offline cache and sending queue, file picker and camera upload.
  • Mobile Meet: LiveKit mobile SDK. CallKit (iOS) and ConnectionService (Android) ring for Meets in DMs; picture-in-picture, background audio, captions.
  • Push: APNs and FCM through the notification engine from P3, with reply and mark-read actions and the phone delay setting honoured.
  • Release: TestFlight and Play internal testing at week 24 for the company beta. Store listings, privacy labels, data-safety forms and review fixes run in weeks 25–28.
  • Integrations (wk 22–28): incoming webhooks, bot users with scoped tokens, a public REST API, app slash commands, a signed Events API, interactive message buttons, and OAuth install with admin approval. GitHub, Jira and Google Drive are built on that same API.
  • The audit log records app installs, scope grants and token use. Apps can be disabled per workspace from the Admin console.

Exit: Toki is live in both stores, and a GitHub pull request posts into #releases with a working Approve button.

Deferred · after the internal beta

Compliance and multi-organisation features

  • Retention policies with the nightly purge job, legal holds and the “no longer available” file state.
  • JSONL exports and the audit hash-chain verifier.
  • External people and shared channels between workspaces; the multi-workspace switcher and Classic layout’s “Create a workspace”.
  • Pick these up when Toki is offered to a second organisation; the data model already has the fields for them.

08 · Cross-cutting

Cross-cutting requirements

Language & time
  • Vietnamese-first content: NFC normalisation on write, accent-folding in search and mention autocomplete.
  • 24-hour clock by default, per-user time zone, local time on profile cards.
  • UI strings in English at launch; Vietnamese UI in P3.
Performance targets
  • Message send to remote render under 300 ms p95 in-region.
  • Channel open under 500 ms with 50 messages, virtualised beyond that.
  • Meet join under 3 s after device check; audio under 150 ms one-way in-region.
Security
  • TLS everywhere, DTLS-SRTP for media, encrypted object storage.
  • Link safety: warn when link text shows a different address (from Advanced prefs).
  • Rate limits on send, upload, invite; virus scan on upload.
Quality
  • Visual regression snapshots of each prototype board in both themes.
  • Playwright end-to-end flows: sign in, post, thread, start Meet, search.
  • Contract tests from the shared Zod schemas.
